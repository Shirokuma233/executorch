# 稀疏验证:在 DDTree 上的方案

> 交接文档。写于 2026-09-02。目标读者是接手这条线的人,假定你熟悉 DFlash / DDTree /
> ExecuTorch QNN 后端,但没有本次会话的上下文。
>
> 结论先行:**稀疏验证在树上不需要任何额外设计,gather 成本与链式完全相同,
> 与树宽无关。** 原因见 §3,那是本文的核心。

---

## 1. 一句话

验证器不需要知道全词表里最好的 token 是哪个,只需要知道草稿给的那个是不是最好的。
前者是 151936 维的 argmax,后者是几十个候选上的排序。

把目标模型 lm_head 的输出限制在草稿提供的候选集上,省掉 `verify_head` 的大部分带宽。
代价是一个可测的近似,见 §4。

> **不要报 "79×"。** 那是回退率为零时的理想值。真实收益必须含回退:
> ```
> 有效行数 = (1 − f) · D · K + f · V        f = 满接受(深度上限)轮占比
> ```
> f 只要几个百分点,`f · 151936` 这一项就淹掉其余一切。f=6% 时 13.9×,
> f=24% 时只剩 4.6×。**节省比例(78–94%)是稳的,倍数不是。**
> 推论:**K 在成本上几乎无所谓,直接取到覆盖饱和为止。**

## 2. 机制

### 2.1 被省掉的是什么

设备实测的一轮分解(SM8750 HTP, Qwen3-4B, tree32_split):

| 阶段 | ms | % |
|---|---|---|
| verify_exec | 46.24 | 60.8 |
| **verify_head** | **10.18** | **13.4** |
| draft_exec | 10.81 | 14.2 |
| draft_head | 7.71 | 10.1 |
| tree_build | 0.015 | 0.02 |

`verify_head` 是**纯搬运**:lm_head 权重 2560 × 151936、8bit、与 embedding 共享
(`tie_word_embeddings: True`),389 MB。除以实测有效带宽 38.7 GB/s = **10.05 ms**,
实测 10.18 ms,对得上到 1%。这 10 ms 里没有计算,只有把 389 MB 拖过 DRAM 一遍。

算力优化对它无效;权重已经 8bit,再压会连带动到输入侧(共享张量)。
**唯一的杠杆是少读几行。**

### 2.2 为什么能少读

`logits = W @ h`,`W` 形状 `[151936, 2560]`,**第 v 行就是 token v 的向量**:

```
logits[v] = ⟨ W[v] , h ⟩
```

第 v 个输出只用到第 v 行,**行与行之间没有任何耦合**。所以它不是"一个大矩阵乘",
是 151936 个各自独立的长度-2560 点积,最后取最大。

只算候选集 `S` 里那些行,得到的数**和全算一遍得到的那些数逐位相同**。
乘法没有被近似、没有被压缩、没有被估计。**唯一变的是 argmax 的范围。**

### 2.3 候选集从哪来

草稿的 lm_head **照跑全词表**(7.71 ms,不动)。`S_d` = 草稿在深度 d 的 top-K。
K = 128 是当前选择,依据见 §6.3。

> 注意这个不对称:省的是**目标模型**那颗头,不是草稿的。正因为草稿跑了全的,
> 才有候选集可用。

## 3. 为什么树上不用改(核心)

这是本文档存在的原因。

### 3.1 候选集是 per-depth 的,不是 per-node 的

DFlash 的草稿是 block-diffusion:**一次双向前向吐出 B=16 个槽的边缘分布**。
DDTree 就是在这些 per-depth marginals 上做 best-first 堆搜索。

所以候选集天然是按深度组织的:

```
S_0, S_1, ..., S_14        草稿在 15 个深度各自的 top-K
```

树在深度 d 上有多少个节点无关紧要——**它们全部共享同一个 S_d**,因为它们全部
出自同一个 marginal。

```
gather 体积 = 15 × K × 2560 字节 = 4.92 MB   (K=128)
```

**这个数和树宽、树形状、budget 都无关。链式是它,budget=31 的树也是它,
budget=63 的树还是它。** 树免费拿到稀疏验证。

### 3.2 走查需要哪些候选集

树的走查是一条路径,**每个深度最多访问一个节点**。节点 i 在深度 `d_i`,
它的 logits 预测第 `d_i + 1` 个新 token,需要 `S_{d_i}`。

路径事先不知道(数据依赖),但路径涉及的深度必然是 0..14 的子集,
所以 gather 全部 15 个就够,不需要任何动态形状。

### 3.3 实现上反而更简单

静态形状下最省事的写法是**不做 per-row 选择**:

```
gather   W[S]        [1920, 2560]      4.92 MB
GEMM     [32, 2560] @ [2560, 1920]  →  [32, 1920]      157 M MAC
slice    第 i 行取 [d_i*K : (d_i+1)*K]                  host 侧
```

- 全部静态形状,没有数据依赖的 shape
- 157 M MAC 对 HTP 是零头(现在是 12.4 G MAC)
- **输出张量从 9.72 MB 缩到 123 KB**(`32 × 151936 × 2` → `32 × 1920 × 2`)。
  这是一笔本来没算进去的额外收益:少写 9.6 MB 到 DRAM,host 也不用再从
  151936 宽的 buffer 里读行。

节点→深度的映射 `d_i` 在建树时就已知(host 侧,0.015 ms),
作为一个 32 个 int32 的输入张量喂进去。

### 3.4 gather 这个原语是现成的

因为 `tie_word_embeddings: True`,**lm_head 的权重就是 embedding 表**,
而 `emb(tokens)` 做的正是在这张表上按行 gather。这个算子已经在图里、已经 lower 过、
已经在设备上跑了几万次。稀疏验证复用的是一条被验证过的路径,不是新原语。

## 4. 正确性

### 4.1 引理:被接受的节点不可能分歧

记 `S_d` 为草稿在深度 d 的 top-K,`x` 为树上某个子节点持有的 token。

树上深度 d+1 的子节点全部出自草稿在深度 d 的候选列表,而 budget = 31,
所以**任何子节点的 rank ≤ 31 < K = 128**,故 `x ∈ S_d` 恒成立。

于是:

```
argmax_V p_d = x   ⟹   argmax_{S_d} p_d = x        (反向不成立)
```

全局第一名在子集里当然还是第一名。所以:

- **精确规则接受某节点时,受限规则也接受,且发出同一个 token。分歧不可能发生在被接受的节点上。**
- **受限规则只可能多接受,不可能少接受**(反向蕴含不成立的那一侧)。

**推论:一轮里唯一可能分歧的,是走查停下来、发出 bonus token 的那一个节点。**

> 前提是 `K ≥ 每深度的最大树宽`。budget=31 时 31 < 128,安全。
> 如果以后 budget 涨到超过 K,这条引理就破了,必须同步涨 K。

### 4.2 bonus token 是怎么来的

走查停在节点 i,发出的 bonus 是目标模型在该节点的预测。精确规则下它是
**全词表 argmax**——这是一轮里目标模型唯一自由选择的 token。

受限规则把这个自由拿掉了:bonus 只能从 `S_{d_i}` 里选。更精确地说,
能走到"发 bonus"这一步说明 `argmax_{S} ≠ 任何子节点`,所以

> **bonus = 草稿在该深度的第 2…K 名候选,由目标模型重新排序后选出的那个。**

一句话概括整个方法:**检查便宜、生成贵,那就把生成也变成检查。**

### 4.3 走查的三种终止,性质完全不同

`walk` 的停止条件 `truth[k] not in maps[node]` 把三件事混在一起了。
43 条 trace / 1070 轮(budget=31 离线重建)拆开:

| 终止原因 | 轮数 | 占比 | 停在深度 中位/均值 | bonus 行候选集覆盖 |
|---|---|---|---|---|
| **真拒绝**(有子节点但都不对) | 636 | 59.4% | 3 / 3.62 | K=8 67.1% / K=32 88.2% / **K=128 96.2%** |
| **子节点用尽**(树没往下长) | 396 | 37.0% | 4 / 5.07 | K=8 77.0% / K=32 91.7% / **K=128 97.5%** |
| **满接受**(走到深度 15) | 38 | 3.6% | 15 / 15.00 | — 无候选集,见 §4.4 |

两点:

1. **37% 的轮次是被预算卡死的,不是被草稿正确率卡死的。** 草稿本来还能对下去,
   只是树没往那个方向长。这是 DDTree 建树策略的机会成本,和稀疏验证无关,
   但它量化了"更好的树形"这件事的天花板。
2. 用完子节点的路径反而**更深、覆盖更好**(5.07 vs 3.62,97.5% vs 96.2%)。
   说得通:best-first 在 marginals 尖锐处长得深而窄,走到叶子说明草稿一路都对;
   尖锐的分布 top-128 覆盖得更好。

### 4.4 唯一的硬回退:走到深度 15

草稿只有 15 个槽,`S_d` 只在 d ≤ 14 存在。走到深度 15 时 bonus 要的是 `S_15`,
不存在。**那一行只能读全头。**

> 注意:"子节点用尽"**不会**触发回退。候选集来自 marginals,和树上那个位置
> 长没长子节点无关。停在深度 4 时 `S_4` 照样有。这点容易搞混。

回退率(树,budget=31,逐 prompt 拟合 n=49,r=0.731):

```
满接受率 ≈ 0.0355 × 平均链长 − 0.164        链长实测范围 2.74–9.54
```

| 平均链长 | 回退率 | 回退成本 | 净省 / 10.05 |
|---|---|---|---|
| 5.56(本次离线模拟) | 3.6% | 0.36 ms | 9.69 ms |
| **6.4(设备工作点)** | **6.3%** | **0.64 ms** | **9.41 ms = 94%** |
| 8.0 | 12.0% | 1.22 ms | 8.83 ms = 88% |

**方法的收益随草稿变强而下降**,这是要主动写出来的局限。

分数据集(树):math500 最坏(链长 6.79 → 回退 7.95%),mt-bench 几乎不触发(1.10%)。

## 5. 实现方案

### 5.1 Runner 改动 `examples/qualcomm/oss_scripts/llama/runner/dflash_token_generator.cpp`

| 行(2026-09-02 的版本) | 现状 | 要改成 |
|---|---|---|
| 1679 `draft_topk_ = tree_budget > 0 ? min(budget, 64) : 1` | 树模式下只算草稿 top-31 | 提到 K=128。**扫描成本已经在付了**(`topk_u16_row` 每深度扫 151936),只是堆大了 |
| 870 `draft_topk()` / 131 `topk_u16_row()` | 已有,host 侧 | 复用。若成为瓶颈,考虑把 TopK 融进草稿头的图 |
| 1594 `run_lm_head(logits_.data)` | 全 `[ar, V]` 写进 `lm_head_logits_buf_` | 换成稀疏头:多一个 `[15, K]` 候选索引输入 + 一个 `[ar]` 节点深度输入,输出 `[ar, K]` |
| 1736/1740 `argmax_u16_row(lg + child*V, V)` | 全词表 argmax | 在该节点深度对应的 K 宽切片上 argmax,再映射回 token id |
| — | — | 新增:走到深度 15 时回退调用全头 |

`tree_child(node, token)` 不用动。需要新增一个 `node → depth` 数组,建树时顺手填。

### 5.2 图侧

新增一张稀疏 lm_head 图,输入:

```
hidden          [1, 32, 2560]      同现在
cand_ids        [15, 128]  int32   host 从 draft_topk 填
node_depth      [32]       int32   host 建树时填
```

输出 `[1, 32, 128]`。内部:`Gather(W, cand_ids.flatten())` → `[1920, 2560]`,
然后 `hidden @ gathered.T` → `[32, 1920]`,按 `node_depth` 切片 → `[32, 128]`。

若 QNN 的动态切片不好写,退一步:直接输出 `[32, 1920]`(123 KB),host 侧切片。
**推荐先走这条**,少一个可能踩坑的算子。

全头那张图**保留**,给深度-15 回退用。

### 5.3 验证顺序

1. host 上先跑通:`ddtree/workspace/run_restricted.py` 已经是链式的参考实现,
   把它改成树版(用 `cmp_ablate.build/walk`),确认 accept 与分歧率和离线预测一致
2. 设备上先只加计数:统计满接受轮的真实占比,坐实 §4.4 里那个 6.3% 的估计
   (现在是离线模拟推的,不是实测)
3. 再上稀疏头

## 6. 已测数据(全部带分母)

### 6.1 分歧率

| 口径 | 值 | 来源 |
|---|---|---|
| 逐验证行(链) | 0.423% | 150 条 fp32 trace / 47713 行 |
| 逐验证行(部署量化图,实跑) | 0.50% | 见 §7,n=8 时的中间值 |
| 逐轮(树,离线) | **3.2%** | 1070 轮,`(636×3.77% + 396×2.53%)/1070` |

三套独立测量互相吻合(链长 ~5.5 时 3.2%/轮 ≈ 0.57%/行)。

**bonus 行才是损失所在**,被接受的行覆盖恒为 100%(引理)。之前把两者混在一个
分母里报,会把真实损失稀释 5–6 倍。**报数时用逐轮或 bonus 行口径。**

### 6.2 分数据集(K=128,链,fp32 trace)

```
math500 0.056% / gsm8k 0.070% / mbpp 0.101% / humaneval 0.133% / mt-bench 2.108%
```

mt-bench 高一个数量级:开放式生成里近义的下一个词太多,top-1/top-2 的 logit 差极小。

### 6.3 K 的选择

只看 bonus 行(真拒绝 / 子节点用尽):

```
K=8    67.1% / 77.0%      三分之一的轮次会改 bonus,不可用
K=32   88.2% / 91.7%
K=128  96.2% / 97.5%      当前选择
```

gather 体积 `15 × K × 2560`:K=32 → 1.23 MB,K=128 → 4.92 MB。
两者相对 10.05 ms 的节省都是零头(0.03 ms vs 0.13 ms),**所以直接取 K=128,
没有理由为了省 0.1 ms 去换 8 个百分点的覆盖**。K=512 也不是不能考虑(19.7 MB,
0.51 ms),但收益递减,且会逼近 §4.1 引理对 budget 的约束边界。

### 6.4 副作用:accept 会变,但没有单调性

**引理只保证同一前缀下、单轮的接受长度不会变短。** 一旦第一次分歧发生,
两条生成的上下文就分叉了,后续每一轮面对的是不同前缀,accept 可以往任何方向走。

> **生成级的平均 accept 没有任何单调性保证。** 早期观察到"一次都没降"并把它
> 归因到引理是过度归因,DDTree/bf16 上已经观察到下降的样本。

而且 Δaccept 和分歧率不是一个尺度:一次分歧若落在"受限接受、精确拒绝"那一侧,
链条会继续往下走,一次就能多吃好几个 token。实测跨度从 −0.7%(1/54 轮分歧)
到 +16%(2/48 轮分歧)。

**报数时应给 Δaccept 的分布,不是均值**,而且不能当成收益——多接受的那些 token
正是精确规则本来要拒绝的,Δaccept 和逐轮分歧率是同一件事的两个视角。

## 7. 当前在跑的实验

`ddtree/workspace/run_restricted.py`,4 个数据集 × 20 条 × K=128,`max_new=320`。

**方法**:同一个进程里对同一条 prompt 跑两遍完整生成,唯一差别是 verifier 的
argmax 范围;草稿、目标前向、接受链、KV 全部不动。

**省一半算力的技巧**:精确跑的时候受限 argmax 是免费的(logits 和候选都已在内存),
旁路报 0 分歧就直接判定两条生成逐位相同(引理保证),只有真出现分歧才补跑第二遍。

**打分**:`dflash/cache/*.jsonl` 里只有 prompt 没有标签,但四个数据集的 HF 缓存都在
本地,按题面 join 后 80/80 命中。`ddtree/workspace/score_restricted.py`:

- gsm8k / math500:抽最后一个 `\boxed{}`,数值归一化后比对
- humaneval:抽代码块,子进程跑官方 `check()`
- mbpp:抽代码块,子进程跑 `test_list`

> **mbpp 的口径警告**:缓存里的 prompt 是裸题面、不含函数签名,
> 而 gold 断言要求特定函数名。打分脚本加了 alias shim(模型只定义一个函数时
> 绑到 gold 要求的名字上)。**两条分支同等对待,所以分支之间的差不受影响,
> 但绝对值不能和 leaderboard 比。**

**n=8 时的中间结果**(不是结论):

```
逐 token 完全相同   5/8
任务判定一致        8/8      ← 这才是要报的指标
精确 4/8 · 近似 4/8          唯一答错的题两条分支一起错,不是近似造成的
```

一个典型案例(mbpp #0):第一个 token 就分歧(`Sure!` vs `Here's`),整段文字完全不同,
但两边的代码都是 `return 5 * side_length`,**都通过**。这就是为什么逐 token 相同率
是个难看且没意义的指标。

单条精确生成约 14–25 分钟(host QDQ 假量化图),预计 6–10 小时跑完。

## 8. 已否决的方案

### 8.1 无损版:证书路线,测死了

想要"稀疏读 + 廉价证明 S 内最大就是全局最大",这样方法就是**精确**的。三种上界:

| 上界 | 做法 | 可判定率 |
|---|---|---|
| Cauchy–Schwarz | `‖h‖ × max 行范数` | **0%** |
| 低秩投影 | r = 64 / 128 / 256 | **0%** |
| 词表聚类 | 1024 簇 + 半径 | **0%** |

根因是 **embedding 各向同性**:前 256 个主方向只削掉行范数的 13%;
聚类半径是行范数的 78%。不是上界选得不好,是这个矩阵没有能被廉价上界抓住的结构。

**证书路线到此为止。** 剩下的只可能是启发式触发的回退(用草稿自己的熵,
因为草稿头跑的是全的),那是工程旋钮,不能写成无损。

这个负结果本身有价值:它标出了无损方案的边界,也解释了为什么现有工作
(FR-Spec / SlimSpec / NanoSpec / DynaSpec)都停在草稿侧。

### 8.2 封顶深度 14 以消除回退:取舍随 accept 变号

满接受轮少发一个 token 换免掉一次全头读:

```
链长 6.4, 回退 6.3%
  吃回退   6.40 / 66.7 ms = 0.0959 tok/ms
  封顶 14  6.34 / 66.1 ms = 0.0959 tok/ms
```

四位有效数字一致。**但这个结论只在低回退率下成立。** 在 DDTree/bf16 的工作点
(accept ≈ 9.8,回退 ≈ 24%)上重算:

```
吃回退   accept 9.81 / 68.4 ms = 0.1434 tok/ms
封顶 14  accept 9.57 / 65.9 ms = 0.1452 tok/ms      ← +1.3%
```

**封顶从打平变成小胜,交叉点大致在回退率 10%(accept ≈ 7)附近。**
所以这不是一个常数结论,是一条随 accept 变号的曲线,部署时要按实际工作点判。

真正干净的修法是让草稿多产一个槽(B=16 只有 15 个可用预测行,要 16 个得 B=17),
那是重训重导,只在本来就要重编时顺手做。

### 8.3 只 gather 前 8 个深度

平均只用到 ~6 个深度的候选,gather 15 个是过度采集 2.3 倍。但 gather 已经只要
0.13 ms 而省下的是 10.05 ms,再抠字节没有意义,只会换来更高的回退率。**不做。**

## 9. 带温度采样

**现状:DFlash 的设备路径就没有温度。** `dflash_token_generator.cpp` 从头到尾是
`argmax_u16_row`;`--temperature` 这个 flag 存在于 `runner.h` / `qnn_llama_runner.cpp`,
但只喂给普通的 token_generator,没接进 DFlash 的验证循环。

**如果要做,带采样反而比贪心更好辩护**,理由如下。

### 9.1 会坏的两处,截断后都变精确

投机采样规则:以 `min(1, p(x)/q(x))` 接受,拒绝后从 `norm(p − q)₊` 重采。

| 机制 | 不截断 | 截断到 S 之后 |
|---|---|---|
| `p(x)/q(x)`,需要 `Z = Σ_{v∈V} e^{z_v}` | 要全词表 ✗ | Z 只在 S 上求和,**K 次 exp 精确算出** |
| `norm(p − q)₊`,需要 p 的完整支撑 | 要全词表 ✗ | 支撑 ⊆ S,**精确** |

### 9.2 有闭式的分布刻画

贪心下近似的代价是"argmax 可能变",0-1 事件,**没有闭式刻画**——这正是会被质疑的地方。
采样下:

```
p̃ = p|_S / p(S)          TV(p, p̃) = 1 − p(S)
```

每个 token 都能精确算出来,还能沿序列叠成上界。

### 9.3 截断本身就是部署标准做法

真实系统跑 `temperature + top_p=0.9/0.95` 或 `top_k=50`,采样器本来只从核内取。
**只要 S ⊇ nucleus,p̃ 就是它本来要用的那个分布——恒等,不是近似。**

所以该测的量是"草稿的 top-K 有没有包住目标的 top-p 核",不是"原始分布落在 S 外的质量"。
后者 K=128 / T=1.0 下是 1.16%(最悲观读法,不截断时方法就是有损的,不藏)。

### 9.4 一条把贡献切干净的事实

**投机采样对任意 proposal q 都是精确的。** 所以:

- **草稿侧砍词表可证无损**——只改接受率,不改输出分布(FR-Spec 走的这条)
- **改 p 才改分布**——稀疏验证动的是目标侧,它是有损的那一半

这条线把"无损贡献"和"有损旋钮"划开,不会混在一起被质疑。

### 机器约束

AMD EPYC 7Y43,192 逻辑核,**只有 AVX2,无 AVX512-BF16 / AMX**。
线程扫描(target 前向 seq=32):192→464ms,**96→353ms(最优)**,48→583ms,24→1031ms。
5 进程 × 38 线程接近聚合最优。

> **CPU 墙钟时间不能当收益报。** 访存/算力比和 HTP 完全不同,而且稀疏版在 CPU 上
> 照样算了全词表 argmax(旁路需要)。收益一律用带宽账表示。

### n=17 时的中间观察(会变,但结构应该稳)

**工作点比设备高很多**:bf16 + budget 32 下 accept 8–10(设备量化版 6.4),
满接受(回退)率 **18–24%**(设备估计 6.3%)。

**一个反向关系**——这是本轮最重要的发现:

| | accept | 回退 | 逐轮分歧 | 成本收益 | 保真度 |
|---|---|---|---|---|---|
| math / code | 8–10 | 20–24% | 0–4% | 差(≈5×) | 好 |
| chat (mt-bench) | 2.5 | 0% | **18.4%** | 好(≈79×) | 差 |

**方法在最省的地方最不准,在最不省的地方最准。** 两端都由同一个量驱动:草稿的确信度。

**根因收敛到一处**:`B=16` 的草稿只提名 15 个 token。这一个约束同时
(a) 压住 accept 天花板、(b) 制造回退、(c) 让"封顶深度 14"方案变得有吸引力。
三个现象一个根因,加大 block size 会同时修掉——但那要重训重导。

### 已知缺口

**mt-bench 没有 gold**(LLM-judge),所以恰恰在保真度最差的数据集上给不出任务准确率。
已确认 **`google/IFEval`(541 条)可用**:开放式指令跟随,但约束程序可验证
(`punctuation:no_comma` / `number_highlighted_sections` / `num_words>=300`)。
**应该补跑**,当时没起是因为 192 核已被占满。
